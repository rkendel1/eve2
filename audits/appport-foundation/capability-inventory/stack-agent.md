## Key structural findings

1. **The model never gets a shell, process, network or git-mutation tool.** The test `crates/stack-agent/tests/capability_surface.rs::no_declared_capability_is_a_shell_a_process_a_network_or_a_git_mutation` asserts this. Strings such as `shell.exec`, `http.get` and `project.git.commit` in the source are negative test cases.
2. **The default model surface is fixed at 10 capabilities:** `project.{list,search,read,write}`, `project.git.{status,diff,diff_stat,log}`, `project.observe` and `pax.test`. Opt-in surfaces add `cli2.tasks`/`cli2.run` (`--cli2-socket`) and operator host capabilities (`--capabilities FILE`, or `--appport ORIGIN`).
3. **The model replies in a JSON decision contract,** with the decisions `request_capability`, `complete`, `escalate` and `block`. It does not use native tool calls. Completion is decided by host predicates over the recorded observations, never by what the model says.
4. **Unused crates (not linked into the `stack-agent` binary):**
   - `chip-session` is used only by `chip-turns`.
   - `chip-turns`, `chip-wasm-host` and `chip-appport-source` have no dependents.
   - `fx-host` is used only by `chip-wasm-host`.
   - `chip-symbol-loop` is a dev-dependency used only by `examples/symbol_loop.rs` (see the `crates/stack-agent/Cargo.toml` comment at about line 71).
   - `chip-compute` is reachable only from demos and benchmarks (`work_demo.rs`, `horizon.rs`, `main.rs --compute-test`), never from `work`.

## Lineage: chip-rs and 3fx

### chip-rs (`c14522a`): **superseded by stack-agent. Belief confirmed. Classify the repo as Retire.**

Evidence:

- **Provenance pins this exact commit.** `stack-agent/docs/migration-provenance.md` names chip-rs `c14522a11e15…` as the copy source. It maps every chip-rs crate to a stack-agent crate by tree hash, with `chip-cli` → `crates/stack-agent`.
- **stack-agent is 12 days newer** (2026-10-28 versus 2026-10-16).
- **stack-agent is a superset.** Its `chip-core` has 25,126 lines against chip-rs's 16,606, and it adds `stuck.rs`. Its `chip-project` has 9,531 lines against 4,793, and adds `policy.rs`, `confine.rs`, `journal.rs` and `lock.rs`. chip-rs's `chip-project/src` has only `git.rs` and `lib.rs`. Crates found only in stack-agent: `chip-agent-state`, `chip-otel`, `chip-cli2`, `chip-experiments`, `chip-appport-source`, `chip-symbol-loop` and the `fx-*` crates.
- **The only chip-rs crate not migrated is `chip-session-memory`:** an experiment using FeltDB as session working memory. It depends on the private `rkendel1/flow_db` repo, was excluded from the chip-rs workspace, and per its lib doc is "a leaf … disabled unless a test or benchmark constructs it". **Retire** it: eve memory and FeltDB records cover it.

## Port details

### P1: SA-30 Stuck guard (Direct port, eve-internal; not an AppPort capability)

1. **Source to preserve:** `crates/chip-core/src/stuck.rs`, all 167 lines. Port `StuckThresholds` (repeated ≥2, default 3; alternating even ≥4, default 4), `detect_stuck`, the pair-equality rule (same capability, same complete typed inputs, same observation kind, status and output; execution ids, receipts and runtime evidence excluded), and `reason`/`reason_with_recovery` with the prefix `stuck: `.
2. **Destination:** an eve hook (`agent/hooks/stuck-guard.ts`) on `call.settled`. It reads the session's recent settled calls (tool name, canonicalized input, result status and output digest) and calls `ctx.cancel("stuck: …")` when the pattern holds. Alternatively, an eve-core harness option. It stays pure and stateless, so it gives the same answer on a resumed session.
3. **Runtime deps:** none beyond eve hooks and session views. Canonical JSON (appport-agent `lib/operations.ts` already has `canonicalize`).
4. **AuthBoundry permission:** none (internal safety mechanism).
5. **Provenance to record:** the pattern (repeated or alternating), the pair count, the tool names and input digests involved, and the thresholds in effect, as a hook-cancel `cause`.
6. **Tests to carry over:** `chip-core/tests/stuck_guard.rs` (thresholds, pair identity, status and kind sensitivity), `stuck_guard_replay.rs` (restored trajectory gives the same answer), `chip-agent-state/tests/stuck_guard.rs` (durable replay). New: an eve integration test that a scripted model repeating `appport_contract` three times ends with `outcome: cancelled`.
7. **Platform gaps:** an eve hook can only cancel the turn. Chip's guard instead converts the work to `escalate`/`blocked` with a recovery hint. Feeding a "you are repeating yourself" note back to the model would need a harness hook or `turn.settled` + `continue`.
